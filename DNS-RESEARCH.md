# Windows VPN Platform: проверка DNS по приложениям

Активное направление, 26.09.2026. Требования: [DNS-DESIGN.md](DNS-DESIGN.md).
Прозрачный DNS выбранных приложений пока **не реализован в установленном клиенте**.
DNS-01 остаётся открытой до измерения изоляции и сетевой приёмки.

## Проверяемая архитектура

Windows VPN Platform предоставляет фильтры приложений и DNS namespaces в одном
VPN-канале. Исследуется отдельный канал только для DNS: Windows выбирает контекст
приложения, а канал пересылает запрос к DNS провайдера через уже существующий
интерфейс OpenVPN. Полный перенос OpenVPN в платформенный плагин пока не требуется
для проверки этой гипотезы.

Подготовлен [стенд](research/VpnPlatform/README.md) для одноразовой Windows 11 VM.
Он отвечает синтетическими DNS-данными и не требует учётной записи VPN-провайдера.
Успешные сборка, локальная COM-фабрика и offline-тесты не доказывают, что Windows
активирует пакет или разделяет DNS-контексты. Реальный результат ещё не получен.

Исследуются два независимых варианта назначения правил:

- Runtime: плагин передаёт EXE-фильтр и DNS namespace в StartWithTrafficFilter.
- Profile: правила приложений и DNS задаются через платформенный VPN-профиль.

[StartWithTrafficFilter](https://learn.microsoft.com/en-us/uwp/api/windows.networking.vpn.vpnchannel.startwithtrafficfilter?view=winrt-26100)
подтверждает наличие этих настроек, но не обещает нужную нам семантику общего кеша.
[VpnPlugInProfile](https://learn.microsoft.com/en-us/uwp/api/windows.networking.vpn.vpnpluginprofile?view=winrt-26100)
предоставляет альтернативную точку настройки. Нельзя объявлять всю платформу
неподходящей по ошибке регистрации пакета или по одному неправильно настроенному варианту.

## Критерий состоятельности

Два обычных EXE одновременно работают в одной Windows. Selected.exe должен
получать ответ VPN DNS, Unselected.exe — обычного DNS на **одно и то же имя**.
Dnscache продолжает работать. Правильный ответ нужен при обоих порядках прогрева,
конкурентных холодных запросах и смене подключения.

Порядок приёмки:

1. Без VPN оба EXE получают контрольный ответ.
2. С VPN без ограничения по EXE оба получают ответ платформенного resolver.
3. Прямой UDP к синтетическому адресу подтверждает точное совпадение EXE-фильтра.
4. Только после этих контролей оцениваются обычные DnsQuery/GetAddrInfo, кеши и
   конкурентность. Для гарантии одновременных запросов нужен барьер responder;
   одинаковое запланированное время запуска само по себе его не заменяет.
5. Проверяются namespace `.`, UDP/TCP, потеря resolver, отсутствие fallback,
   повторное подключение с тем же именем и обычный Chrome.
6. При интеграции с OpenVPN — реальные DNS из PUSH, захват на физических/VPN
   интерфейсах, отзыв поколения DNS и неизменность невыбранных приложений.

Прототип и точная матрица: [VM runbook](research/VpnPlatform/VM-RUNBOOK.md).
Эксперимент с регистрацией пакета, сертификатом и VPN/DNS-настройками выполняется
в отдельной VM, не на рабочей Windows. VM нужна для испытаний механизма; модель
продукта остаётся запуском выбранных приложений на обычном рабочем столе.

## Что уже можно использовать

UI получает DNS-метаданные из аутентифицированного OpenVPN management-канала,
публикует их с идентичностью сессии/адаптера и отзывает при reconnect.
В Rust сохранён явно включаемый частный DNS broker с UDP/TCP transport, привязанным
к VPN, проверкой вопроса/ответа и отзыва текущей сессии. UI его не запускает.

Платформенный плагин ещё не подключён к этому broker. Нынешняя проверка broker
по EXE клиента не удостоверяет происхождение запроса общей службы Windows.
До интеграции нужно определить доверенную идентичность пакета, IPC-разрешения
и источник политики приложения. Добавление Dnscache в общий allowlist не доказывает
разделение и не является допустимым способом заставить тест пройти.

## Ограничения

WFP/WinDivert видят владельца endpoint. Для общей DNS-службы это не автоматически
исходное приложение. Корреляция по имени и времени не решает кеш и конкурентные
запросы. [WFP conditions](https://learn.microsoft.com/en-us/windows/win32/fwp/filtering-condition-identifiers-).

SDK содержит DNS connection policy с AppId, но её семантика выбора resolver,
кеша и владения правилами не подтверждена. Поддерживаемый VPN-профиль имеет
приоритет над прямыми недокументированными setters.
[Декларации SDK](https://github.com/microsoft/win32metadata/blob/5c5efbc01d4c87f6830ec304d42777991d533154/generation/WinSDK/RecompiledIdlHeaders/um/WinDNS.h#L1558).

Собственный DoH/DoT приложения — отдельная граница. Направить HTTPS в VPN
не означает заменить выбранный приложением DNS сервером провайдера.
Microsoft указывает, что собственные DNS-реализации обходят NRPT.
[VPNv2 CSP](https://learn.microsoft.com/en-us/windows/client-management/mdm/vpnv2-csp#deviceprofilename-domainnameinformationlist),
[DoH, RFC 8484](https://www.rfc-editor.org/rfc/rfc8484.html).

Резервный PIA-подход сохранён как справочная альтернатива, но не разрабатывается:
он меняет общую Dnscache, что требует отдельного решения о допустимости воздействия
на систему. [Исходный механизм](https://github.com/pia-foss/desktop/blob/3.7.2/daemon/src/win/win_dnscachecontrol.h).
