# DNS по приложениям: резервный PIA-подход

Активное направление по решению пользователя, 26.09.2026. Требования и ограничения:
[DNS-DESIGN.md](DNS-DESIGN.md). Экспериментальный режим выключен по умолчанию.
DNS-01 остаётся открытой до живой проверки перенаправления и восстановления служб.

**Результат живой проверки 1.3.2:** на Windows 26200.9457 / 25H2 подмена привела
к немедленной ошибке 1722 (`RPC_S_SERVER_UNAVAILABLE`) в DnsQuery_W STANDARD и
WIRE_ONLY и ошибке 11002 в GetAddrInfoW. При тех же наблюдаемых stub/guardian
прямые UDP/TCP запросы к системному DNS получили положительные ответы; после
отключения все пять проб снова успешны. Предположение о fallback внутри приложения
на этом ПК опровергнуто для проверенных обычных Windows API. Исходники PIA не
являются доказательством совместимости нашей реализации с этой конфигурацией.
[Подробный результат](VALIDATION.md#подтверждённый-отказ-windows-dns-api-при-подмене--26092026).

## Выбранный механизм

В PIA общий DNS Client временно заменяется службой-заглушкой. Согласно исходникам
PIA, это позволяет приложениям выполнять обычные DNS-запросы в своих процессах,
после чего сетевые фильтры могут различать их по EXE. PIA сохраняет исходные
ImagePath/Type службы и возвращает эти значения после запуска заглушки.
[Описание PIA](https://github.com/pia-foss/desktop/blob/3d76d75c7e5693812aa1b72108cb44df7397dd32/daemon/src/win/win_dnscachecontrol.h),
[реализация](https://github.com/pia-foss/desktop/blob/3d76d75c7e5693812aa1b72108cb44df7397dd32/daemon/src/win/win_dnscachecontrol.cpp).

Наш dataplane использует существующие IPv4 UDP/TCP bridges. Для выбранного EXE
обычный запрос на порт 53 направляется к DNS из текущей сессии OpenVPN; приложению
ответ возвращается от исходного endpoint. Сокет привязывается к проверенному VPN
интерфейсу. Заглушка сама по себе DNS не перенаправляет и resolver не подменяет.

**Компромисс:** меняется общая служба и общий кеш Windows. DNS-серверы и маршруты
невыбранных приложений должны сохраняться, но утверждать, что остальная система
совсем не затронута, нельзя. Собственный DoH/DoT также не превращается в DNS
провайдера этим способом. Для shared-service callers исходная принадлежность
запроса остаётся отдельным ограничением.

## Восстановление — часть механизма

Реализация не копирует GPL-код PIA. Отдельная собственная LocalSystem-служба
наблюдает точные экземпляры UI и backend и отвечает за восстановление независимо
от их Job. Исходные параметры записываются в защищённый журнал с flush до первого
изменения. Автоматический запуск после сбоя/перезагрузки предназначен для
восстановления; новая активация требует отдельной подтверждённой lease.

Общий svchost, неизвестная конфигурация, неполная проверка владельца или чужое
изменение параметров означают отказ. Нельзя переносить fallback PIA, который
завершает другой NetworkService host. Число служб, видимых через одно перечисление
SCM, само по себе не доказывает отсутствие соседей: недоступные службы могут быть
пропущены. [EnumServicesStatusEx](https://learn.microsoft.com/en-us/windows/win32/api/winsvc/nf-winsvc-enumservicesstatusexw).

Нужно сохранять фактический исходный Type: на текущем ПК read-only проверка
показала `0x10`, а не `0x20`. Windows различает отдельный и общий процесс службы
через [QUERY_SERVICE_CONFIG](https://learn.microsoft.com/en-us/windows/win32/api/winsvc/ns-winsvc-query_service_configa).
PIA требует исходный `SHARE_PROCESS` (`0x20`); разрешение исходного `0x10` в
1.3.0–1.3.2 было нашим неподтверждённым расширением. В 1.3.3 новые acquire для
него отклоняются до подмены. Причинность самого Type для RPC 1722 не доказана,
поэтому менять системный Type ради обхода запрета нельзя. Для восстановления
старых lease `0x10` сохраняется точная проверка NetworkService без `-s`; для
`0x20` нужен явный `-s Dnscache`. Проверки Microsoft svchost, учётной записи и
отсутствия соседних служб остаются в обоих путях восстановления.

Реестр службы на рабочем ПК при разработке не менялся. Unit-тесты журнала и
аварийных переходов не заменяют испытания со службой, перезагрузкой и захватом DNS.

## Предыдущее направление: Windows VPN Platform

Исследование сохранено, разработка приостановлена. Созданная тестовая VM не дошла
до приёмки Windows/Tools/snapshot; впоследствии её VMX/VMDK отсутствовали по
подготовленному пути. Платформенный пакет ни в госте, ни на хосте не активировался.
Это не отрицательный результат DNS-архитектуры: живого результата нет.

### Сохранённая гипотеза

Windows VPN Platform предоставляет фильтры приложений и DNS namespaces в одном
VPN-канале. Исследуется отдельный канал только для DNS: Windows выбирает контекст
приложения, а канал пересылает запрос к DNS провайдера через уже существующий
интерфейс OpenVPN. Полный перенос OpenVPN в платформенный плагин пока не требуется
для проверки этой гипотезы.

Подготовлен [стенд](research/VpnPlatform/README.md) для одноразовой Windows 11 VM.
Он отвечает синтетическими DNS-данными и не требует учётной записи VPN-провайдера.
Успешные сборка, локальная COM-фабрика и offline-тесты не доказывают, что Windows
активирует пакет или разделяет DNS-контексты. Реальный результат ещё не получен.

Исследуются два независимых варианта назначения правил:

- Runtime: плагин передаёт EXE-фильтр и DNS namespace в StartWithTrafficFilter.
- Profile: правила приложений и DNS задаются через платформенный VPN-профиль.

[StartWithTrafficFilter](https://learn.microsoft.com/en-us/uwp/api/windows.networking.vpn.vpnchannel.startwithtrafficfilter?view=winrt-26100)
подтверждает наличие этих настроек, но не обещает нужную нам семантику общего кеша.
[VpnPlugInProfile](https://learn.microsoft.com/en-us/uwp/api/windows.networking.vpn.vpnpluginprofile?view=winrt-26100)
предоставляет альтернативную точку настройки. Нельзя объявлять всю платформу
неподходящей по ошибке регистрации пакета или по одному неправильно настроенному варианту.

### Критерий состоятельности платформенной гипотезы

Два обычных EXE одновременно работают в одной Windows. Selected.exe должен
получать ответ VPN DNS, Unselected.exe — обычного DNS на **одно и то же имя**.
Dnscache продолжает работать. Правильный ответ нужен при обоих порядках прогрева,
конкурентных холодных запросах и смене подключения.

Порядок приёмки:

1. Без VPN оба EXE получают контрольный ответ.
2. С VPN без ограничения по EXE оба получают ответ платформенного resolver.
3. Прямой UDP к синтетическому адресу подтверждает точное совпадение EXE-фильтра.
4. Только после этих контролей оцениваются обычные DnsQuery/GetAddrInfo, кеши и
   конкурентность. Для гарантии одновременных запросов нужен барьер responder;
   одинаковое запланированное время запуска само по себе его не заменяет.
5. Проверяются namespace `.`, UDP/TCP, потеря resolver, отсутствие fallback,
   повторное подключение с тем же именем и обычный Chrome.
6. При интеграции с OpenVPN — реальные DNS из PUSH, захват на физических/VPN
   интерфейсах, отзыв поколения DNS и неизменность невыбранных приложений.

Прототип и точная матрица: [VM runbook](research/VpnPlatform/VM-RUNBOOK.md).
Эксперимент с регистрацией пакета, сертификатом и VPN/DNS-настройками выполняется
в отдельной VM, не на рабочей Windows. VM нужна для испытаний механизма; модель
продукта остаётся запуском выбранных приложений на обычном рабочем столе.

## Общие компоненты

UI получает DNS-метаданные из аутентифицированного OpenVPN management-канала,
публикует их с идентичностью сессии/адаптера и отзывает при reconnect.
В Rust сохранён явно включаемый частный DNS broker с UDP/TCP transport, привязанным
к VPN, проверкой вопроса/ответа и отзыва текущей сессии. UI его не запускает.

Платформенный плагин ещё не подключён к этому broker. Нынешняя проверка broker
по EXE клиента не удостоверяет происхождение запроса общей службы Windows.
До интеграции нужно определить доверенную идентичность пакета, IPC-разрешения
и источник политики приложения. Добавление Dnscache в общий allowlist не доказывает
разделение и не является допустимым способом заставить тест пройти.

## Ограничения

WFP/WinDivert видят владельца endpoint. Для общей DNS-службы это не автоматически
исходное приложение. Корреляция по имени и времени не решает кеш и конкурентные
запросы. [WFP conditions](https://learn.microsoft.com/en-us/windows/win32/fwp/filtering-condition-identifiers-).

SDK содержит DNS connection policy с AppId, но её семантика выбора resolver,
кеша и владения правилами не подтверждена. Поддерживаемый VPN-профиль имеет
приоритет над прямыми недокументированными setters.
[Декларации SDK](https://github.com/microsoft/win32metadata/blob/5c5efbc01d4c87f6830ec304d42777991d533154/generation/WinSDK/RecompiledIdlHeaders/um/WinDNS.h#L1558).

Собственный DoH/DoT приложения — отдельная граница. Направить HTTPS в VPN
не означает заменить выбранный приложением DNS сервером провайдера.
Microsoft указывает, что собственные DNS-реализации обходят NRPT.
[VPNv2 CSP](https://learn.microsoft.com/en-us/windows/client-management/mdm/vpnv2-csp#deviceprofilename-domainnameinformationlist),
[DoH, RFC 8484](https://www.rfc-editor.org/rfc/rfc8484.html).

PIA-подход стал активным резервным направлением. Наличие работающего аналога
не заменяет проверку этой реализации на используемой версии Windows.
