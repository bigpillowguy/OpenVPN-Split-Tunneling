# DNS выбранных приложений через Windows VPN Platform

Активное направление — Windows VPN Platform. Реализация системного выбора
DNS-контекста ещё проходит исследование. Текущий клиент сохраняет обычный DNS;
подключение VPN и список полученных DNS-серверов не означают защиту DNS.
[Состояние исследования](DNS-RESEARCH.md), [стенд](research/VpnPlatform/README.md).

## Требование

- Выбранный EXE разрешает имена через DNS, предоставленный активным VPN.
- DNS transport проходит через подтверждённый VPN-интерфейс этой сессии.
- Невыбранные приложения сохраняют свои DNS-серверы, маршруты и рабочую Dnscache.
- Настройки отдельных браузеров, расширения, Chrome flags и ручной proxy
  не являются механизмом реализации.
- Отсутствие DNS VPN не маскируется fallback на системный или публичный resolver.
- Приложения запускаются обычным способом и с обычными правами пользователя.

## Механизм и граница доказательства

Исследуется дополнительный VPN-канал только для DNS с платформенной политикой
приложений. Его DNS transport предполагается связать с существующей сессией
OpenVPN. Runtime traffic filters и профильные правила испытываются отдельно.
Присутствие AppId в API не доказывает разделение кеша и одинакового имени
между выбранным и невыбранным EXE.

Текущий runtime-профиль OpenVPN исключает локальные/pushed DNS/DHCP и маршруты.
Поэтому система сохраняет свои настройки. Метаданные DNS из PUSH получаются
отдельно; они пригодны для будущей интеграции, но не меняют DNS сами по себе.

Собственный DoH/DoT приложения не подчиняется автоматически системному resolver.
Туннелирование HTTPS не меняет его DNS-получателя. Поддержка такого поведения
должна быть определена отдельно, до обещания универсальности.
[VPNv2 DNS policy](https://learn.microsoft.com/en-us/windows/client-management/mdm/vpnv2-csp#deviceprofilename-domainnameinformationlist),
[RFC 8484](https://www.rfc-editor.org/rfc/rfc8484.html).

## Контракт DNS-метаданных будущей реализации

Проверенный источник для текущей политики — realtime `>LOG` аутентифицированного
management-канала. OpenVPN 2.7.4 и 2.6.14 формируют запись о полученном PUSH до
pull-фильтров и проверки разрешённых опций. Отвергнутые DNS-директивы нельзя
восстановить из текущих UPDOWN environment-метаданных. Конкретный текст записи
PUSH является проверенным для этих версий форматом, а не отдельным стабильным
DNS API: неизвестный формат должен давать состояние «не определён».

Текущий management-клиент отправляет `log on` до `hold release`, ожидает подтверждение
и использует `verb 3` с принудительным `mute 0`; иначе разрешённый профилем `mute` способен
скрыть часть метаданных ещё до management-канала. Предел чтения C# — 16 KiB
с подсчётом UTF-8 байтов; он покрывает upstream log buffer размером 10240 байт.
PUSH с `push-continuation` публикуется только после полного набора фрагментов
и подтверждённого подключения. При UP нельзя стереть DNS из предшествующего
PUSH новой попытки. PUSH_UPDATE требует отдельной модели изменений; запись в
логе сама по себе не подтверждает применение обновления. До её реализации
DNS-update отзывает готовность DNS, а не оставляет прежние серверы действующими.
Raw LOG/PUSH не сохраняется и не включается в исключения: upstream redaction
не покрывает любые секретные параметры.

Источники: [management protocol](https://github.com/OpenVPN/openvpn/blob/v2.7.4/doc/management-notes.txt),
[PUSH и обновления](https://github.com/OpenVPN/openvpn/blob/v2.7.4/src/openvpn/push.c),
[permission mask](https://github.com/OpenVPN/openvpn/blob/v2.7.4/src/openvpn/init.c),
[mute](https://github.com/OpenVPN/openvpn/blob/v2.7.4/src/openvpn/error.c),
[redaction](https://github.com/OpenVPN/openvpn/blob/v2.7.4/src/openvpn/misc.c).

Список DNS в session-файле сам по себе не обеспечивает изоляцию. Нельзя получать
его ценой отмены `route-nopull`, угадывать по gateway или брать с произвольного
VPN-адаптера. Локальные DNS-директивы профиля и полученные от сервера настройки
имеют разное происхождение и должны различаться.

DNS публикуется атомарно с идентичностью текущей сессии, процесса и адаптера.
Нужны отдельные состояния: ещё не получен, не предоставлен, невалиден,
не поддерживается, доступен. Пустой массив не доказывает отсутствие DNS у VPN.
Доступность метаданных нельзя показывать как действующую защиту DNS.

OpenVPN 2.7 поддерживает приоритеты и группы серверов, числовые IPv4/IPv6
endpoints с портами, transport, SNI, DNSSEC и доменные ограничения. Поддерживаемое
подмножество требуется определить явно; остальные настройки нельзя молча
превращать в обычный IPv4 DNS. Обычный DNS должен учитывать UDP и TCP fallback.
Источник: [OpenVPN 2.7 manual](https://openvpn.net/community-docs/community-articles/openvpn-2-7-manual.html).

Размеры, число серверов и порты ограничиваются, адреса валидируются. Смена DNS
при прежнем IP/interface тоже меняет поколение DNS: ожидающие запросы отменяются,
кеши разных поколений не смешиваются. При DOWN, reconnect и выходе процесса
метаданные отзываются вместе с привязкой туннеля. Системный resolver не служит
неявной заменой отсутствующего или неподдерживаемого VPN DNS.

## Приёмка до включения в установщик

1. В одноразовой VM подтвердить активацию пакета, обычный DNS, DNS канала без
   EXE-фильтра и точное совпадение EXE прямым UDP. Ошибки стенда не считать
   отрицательным результатом архитектуры.
2. Два DNS-сервера возвращают разные ответы на одно имя. Выбранный и невыбранный
   EXE получают свой ответ при обоих порядках прогрева, конкурентных холодных
   запросах, reconnect и сохранении имени между подключениями.
3. Проверить namespace `.`, Win32 DNS APIs, direct UDP/TCP, AAAA, CNAME,
   truncation/TCP fallback, NXDOMAIN, таймаут и отсутствие DNS VPN.
4. Проверить обычный Chrome и другие многопроцессные приложения с их стандартной
   sandbox, свежие/существующие процессы, shared service callers и PID reuse.
5. При подключении transport к OpenVPN подтвердить DNS провайдера и точный
   актуальный интерфейс, смену DNS/generation, backend crash, удаление выбора,
   отсутствие обычного DNS egress выбранного приложения вне туннеля.
6. Состояние Dnscache и DNS невыбранного приложения сохраняется. Изменения
   тестовой VM должны полностью сниматься возвратом к чистому snapshot.
7. BrowserLeaks — дополнительное наблюдение. Принадлежность запросов и capture
   физических/VPN интерфейсов являются решающими сетевыми доказательствами.
